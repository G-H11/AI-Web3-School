# 2026-06-03 Z.AI Long-Horizon Task — AI Agent 工作流拆解

> 📅 2026-06-03 | 提问：QQ | 关联：Hackathon Track 2 Z.AI

## 核心问题

如果选择 Z.AI｜Web3 × Long-Horizon Task，AI Agent 如何拆解复杂任务、持续调用工具、迭代修复，并完成从需求到交付的 Web3 工作流？

---

## 一、任务拆解：从模糊需求到可执行计划

以「开发一个 ERC-20 代币空投工具，部署到 Sepolia 测试网」为例：

### Step 1: 需求结构化
AI Agent 将模糊需求拆解为原子化任务：
- ① 编写 MerkleAirdrop 合约（claim 模式，省 gas）
- ② 编写批量转账合约（push 模式）
- ③ 部署脚本 + 合约验证
- ④ 前端交互页面
- ⑤ README + Demo 视频脚本

### Step 2: 依赖分析
识别任务间的并行/串行关系：
- ①② 可并行编写 → ③ 依赖 ①② → ④ 依赖 ③ → ⑤ 依赖 ③④

### Step 3: 工具映射
每个子任务映射到具体工具：
| 子任务 | 工具 |
|--------|------|
| 编写 Solidity | 代码生成 |
| 编译合约 | forge / hardhat |
| 部署合约 | forge script + RPC |
| 验证合约 | etherscan API |
| 前端页面 | React/Vite |
| 测试 | forge test |

---

## 二、持续工具调用（基于 MCP 协议）

Agent 不是一次性生成代码，而是形成反馈闭环：

```
终端工具 → forge init/build/test
文件工具 → 写合约/改合约/读错误日志
链上工具 → 部署/验证/查交易状态
浏览器   → 查 Etherscan/docs/faucet
```

每步输出 = 下一步输入。

---

## 三、迭代修复

| 错误类型 | Agent 修复策略 |
|----------|---------------|
| 编译错误 | 解析报错行号 → patch 修复 → 重新 build |
| 测试失败 | 读测试输出 → 分析 expected vs actual → 修正逻辑 |
| 链上 revert | 解析 revert reason → 查 gas tracker → 调整 → 重部署 |
| 合约验证失败 | 比对 bytecode → 检查 compiler version → 重新验证 |

GLM-5.1 亮点：8 小时自主执行，给任务去睡觉，醒来验收。

---

## 四、完整交付物

一句话需求 → 拆解计划 → 合约代码（迭代 1→2→3）→ 测试套件 → 部署+验证 → 前端页面 → README → Demo 视频脚本 → GitHub 仓库 → Hackathon 提交

## 五、Track 1 vs Track 2 对比

| 维度 | Track 1 Cobo | Track 2 Z.AI |
|------|-------------|-------------|
| 核心挑战 | 资金安全 + 权限边界 | 长周期自主执行 |
| Agent 角色 | 资金守门人 | 全栈开发者 |
| 工具调用 | Cobo Wallet SDK（1-2 个） | MCP 全工具链 |
| 迭代重点 | 权限策略 → 安全审计 | 编译错误 → 测试失败 → revert |
| 交付验收 | 一次安全的资金闭环 | 可运行的 GitHub 仓库 |

---

## 关键启发

1. **Long-Horizon 的核心不是"生成更快"而是"自主纠错"**——Agent 的价值在迭代循环中体现
2. **MCP 协议是工具层标准**——Agent 通过同一种协议调用 forge/git/web/chain 等不同工具
3. **错误处理是区分玩具和可用产品的分水岭**——能处理 compile error、test failure、on-chain revert 三种错误的 Agent 才是真正的「自主 Agent」
