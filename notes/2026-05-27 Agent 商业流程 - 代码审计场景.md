> 日期：2026-05-27

---

## 一、场景选定：AI 智能合约审计 Agent

**场景描述**：一个去中心化的 AI 代码审计市场。项目方需要审计自己的智能合约，可以在市场上发布任务；AI Agent 报价、执行审计、交付报告；项目方验收后付款。全程链上可追溯。

---

## 二、角色定义

| 角色 | 谁 | 做什么 | 持有什么 |
|------|-----|--------|----------|
| **Client（下单方）** | 项目方 / DeFi 协议 | 发布审计需求，设定预算，验收报告 | 资金（需支付审计费） |
| **Provider（执行方）** | AI 审计 Agent | 接收任务，执行代码审计，生成报告 | 能力证明（声誉 + staking） |
| **Evaluator（验收方）** | 可以是 Client 自己，也可以是第三方评审 DAO | 验证审计报告质量，判定通过/不通过 | 声誉 + 专业判断力 |
| **Arbiter（仲裁方）** | 去中心化仲裁合约 / Kleros 类型陪审团 | 争议时裁决，分配资金 | 仲裁权（由治理赋予） |
| **Registry（注册方）** | 链上 Agent 注册表 | 记录 Agent 身份、声誉、验证历史 | 不可篡改的链上记录 |

## 三、完整 Payment / Commerce 流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                    AI 代码审计 Agent 商业流程                          │
│                                                                     │
│  1.报价 ──→ 2.预算授权 ──→ 3.执行 ──→ 4.交付 ──→ 5.验收              │
│                                            ↓                        │
│                              7.记录证明 ←── 6.付款/退款/争议           │
└─────────────────────────────────────────────────────────────────────┘
```

### 阶段 1：报价（Quote）

| 步骤 | 谁 | 动作 | 链上/链下 |
|------|-----|------|-----------|
| 1.1 | Client | 发布审计需求：「审计一个 AMM 池合约，包含 swap / addLiquidity / removeLiquidity，约 500 行 Solidity」 | 发布到 Agent 市场/Discovery |
| 1.2 | Provider | 收到匹配通知，分析需求复杂度，生成报价单 | 链下（AI 分析） |
| 1.3 | Provider | 提交报价：`0.5 ETH`，预计交付时间 24h，附上过往审计案例的链上证明 | 链上报价消息（签名） |
| 1.4 | Client | 比较多个 Agent 的报价和声誉评分，选出最合适的 | 链下比较 |

> **信任基础**：Client 依靠 ERC-8004 的 Reputation Registry 查看 Agent 的历史评分。

---

### 阶段 2：预算授权（Budget Authorization）

| 步骤 | 谁 | 动作 | 关键保证 |
|------|-----|------|----------|
| 2.1 | Client | 调用链上合约 `setBudget(jobId, 0.5 ETH)` | Client 确认愿意支付 |
| 2.2 | Client | 调用 `fund(jobId, 0.5 ETH)`，资金从 Client 钱包进入**托管合约（Escrow）** | 资金锁定，Client 无法单方面取回 |
| 2.3 | 合约 | 状态变更：`Open → Funded` | 不可逆（除非 Evaluator 拒绝或超时） |
| 2.4 | 合约 | 设置 `expiredAt = now + 48h`（24h 执行 + 24h 验收缓冲） | 防无限等待 |

> **为什么这一步必须人工确认**：涉及资金锁定。Client 必须亲眼确认托管合约地址正确、金额正确、过期时间合理。**不能由 Agent 自动签署 fund 交易。**

---

### 阶段 3：执行（Execution）

| 步骤 | 谁 | 动作 | 是否可自动化 |
|------|-----|------|--------------|
| 3.1 | Provider Agent | 从链上读取合约源码 | ✅ 自动 |
| 3.2 | Provider Agent | 运行静态分析（Slither / Mythril） | ✅ 自动 |
| 3.3 | Provider Agent | 运行符号执行 / Fuzzing | ✅ 自动 |
| 3.4 | Provider Agent | LLM 审查业务逻辑、权限、经济模型 | ✅ 自动 |
| 3.5 | Provider Agent | 生成审计报告（Markdown，含漏洞等级、复现步骤、修复建议） | ✅ 自动 |

> 执行阶段完全自动化。Agent 无需人工介入。

---

### 阶段 4：交付（Delivery）

| 步骤 | 谁 | 动作 | 链上/链下 |
|------|-----|------|-----------|
| 4.1 | Provider Agent | 将审计报告上传到 IPFS / Arweave，获得内容哈希 `QmXxx...` | 链下存储 |
| 4.2 | Provider Agent | 调用 `submit(jobId, deliverableHash)` 提交交付物哈希 | **链上** |
| 4.3 | 合约 | 状态变更：`Funded → Submitted` | 链上 |

> **deliverableHash** 不是报告全文，而是报告在 IPFS 上的内容标识符（CID）。这保证交付物不可篡改。

---

### 阶段 5：验收（Acceptance）

| 步骤 | 谁 | 动作 | 是否必须人工 |
|------|-----|------|--------------|
| 5.1 | Evaluator | 从 IPFS 下载审计报告，阅读内容 | 🔴 **必须人工** |
| 5.2 | Evaluator | 验证报告中发现的问题是否真实（复现漏洞） | 🔴 **必须人工** |
| 5.3 | Evaluator | 评估报告质量：覆盖度、深度、建议质量 | 🔴 **必须人工** |
| 5.4 | Evaluator | 决策：`complete` 或 `reject` | 🔴 **必须人工** |

> **验收是最大的人工确认环节**。代码审计的结果直接影响协议安全——不能交给另一个 AI 自动判定"另一个 AI 做得好不好"，否则形成循环信任问题。

---

### 阶段 6：付款 / 退款 / 争议（Payment / Refund / Dispute）

#### 6A. 验收通过 → 付款

| 步骤 | 谁 | 动作 |
|------|-----|------|
| 6A.1 | Evaluator | 调用 `complete(jobId, reasonHash)` |
| 6A.2 | 合约 | 状态变更：`Submitted → Completed` |
| 6A.3 | 合约 | 托管资金 `0.5 ETH` 从 Escrow 转给 Provider |
| 6A.4 | 合约 | 可选：`0.025 ETH`（5%）作为平台费转给协议 Treasury |
| 6A.5 | Registry | 增加 Provider 的成功完成记录 → 声誉 +1 |

#### 6B. 验收不通过 → 退款

| 步骤 | 谁 | 动作 |
|------|-----|------|
| 6B.1 | Evaluator | 调用 `reject(jobId, reasonHash)`，附上拒绝原因 |
| 6B.2 | 合约 | 状态变更：`Submitted → Rejected` |
| 6B.3 | 合约 | 托管资金全额退还给 Client |
| 6B.4 | Registry | 记录拒绝原因 → Provider 声誉受影响 |

#### 6C. 超时 → 自动退款

| 步骤 | 谁 | 动作 |
|------|-----|------|
| 6C.1 | 任何人 | `block.timestamp >= expiredAt` 时调用 `claimRefund(jobId)` |
| 6C.2 | 合约 | 状态变更：`Funded/Submitted → Expired` |
| 6C.3 | 合约 | 托管资金全额退还给 Client |

#### 6D. 争议升级 → 仲裁

当 Provider 不服 Evaluator 的 `reject` 决定时：

| 步骤 | 谁 | 动作 |
|------|-----|------|
| 6D.1 | Provider | 向仲裁合约提交争议请求，附带 staking 押金（防止滥用） |
| 6D.2 | Arbiter | 调取 `deliverableHash` → 从 IPFS 获取报告 |
| 6D.3 | Arbiter | 独立审查（可由人类陪审团 / 多签名委员会执行） |
| 6D.4 | Arbiter | 裁决：维持原判 | 推翻 → 释放资金给 Provider + 罚没 Evaluator 押金 |
| 6D.5 | 合约 | 执行裁决，更新双方声誉记录 |

> **仲裁是安全网**。正常流程 95% 不走仲裁；但仲裁的存在本身约束了 Evaluator 不能随意拒绝。

---

### 阶段 7：记录证明（Proof of Record）

| 维度 | 记录内容 | 存储位置 |
|------|----------|----------|
| **任务创建** | jobId、Client、需求描述哈希 | 链上日志（event） |
| **报价** | Provider、报价金额、有效期 | 链上 + ERC-8004 Reputation Registry |
| **资金锁定** | fund 交易哈希、金额、时间戳 | 链上 |
| **交付** | deliverableHash（IPFS CID） | 链上 + IPFS |
| **验收结果** | complete/reject + reasonHash + Evaluator 签名 | 链上 |
| **付款** | 转账记录（Escrow → Provider） | 链上 |
| **争议** | 仲裁请求、证据、裁决 | 链上 |
| **声誉更新** | 成功/失败次数、平均评分 | ERC-8004 Reputation Registry |

> 所有这些记录构成**完整的审计追溯链**——任何一个环节都可以独立验证，不需要信任任何单一方。

## 四、必须人工确认的操作（重点汇总）

| 操作 | 理由 |
|------|------|
| 🔴 Client 调用 `fund()` 锁定资金 | 涉及真实资产，必须亲眼确认合约地址和金额 |
| 🔴 Evaluator 调用 `complete()` / `reject()` | 验收判断需要专业能力 + 责任心，AI 不能自评自审 |
| 🔴 争议仲裁裁决 | 涉及利益冲突，必须由独立第三方判断 |
| 🟡 Provider 设置报价 | 可选自动（AI 按复杂度公式计算）或人工复核 |
| 🟢 代码分析执行 | 完全由 Agent 自动化 |
| 🟢 报告生成与提交 | 完全由 Agent 自动化 |
| 🟢 超时退款 `claimRefund()` | 任何人都可触发，无人工确认要求 |

## 五、加分：x402 vs ERC-8183 协议对比

这两个协议覆盖 Agent 商业流程的**不同层次**，彼此互补。

### x402 — 支付验证层（HTTP 402 Payment Required）

| 维度 | 说明 |
|------|------|
| **解决什么** | **微支付 + 身份验证**：API 调用者必须先付款才能访问服务 |
| **工作方式** | HTTP 402 状态码 + 链上支付验证。Server 返回 `402 Payment Required` + 收款地址和金额，Client 签名链上交易并附带支付证明，Server 验证后放行 |
| **典型流程** | `GET /audit-report/QmXxx` → Server: 402 + `{amount: 0.01 ETH, to: 0x...}` → Client 链上付款 → 重试请求附带 txHash → Server 验证到账 → 返回报告 |
| **解决哪一段** | **报价 → 支付 → 内容交付**：即"一手交钱一手交货"的原子化交易 |
| **信任模型** | 按需付费，无托管。Client 每次请求都即时支付 |
| **适合** | 小额、高频、即时交付的服务（API 调用、数据查询、单次推理） |

### ERC-8183 — 托管结算层（Agentic Commerce Protocol）

| 维度 | 说明 |
|------|------|
| **解决什么** | **托管 + 验收 + 结算**：大额任务需要第三方验收才能释放资金 |
| **工作方式** | 链上状态机：`Open → Funded → Submitted → Completed/Rejected/Expired`。资金由智能合约托管，Evaluator 是唯一有权验收的人 |
| **典型流程** | Client → `fund(0.5 ETH)` → Provider → `submit(cid)` → Evaluator → `complete()` → Provider 收到 0.5 ETH |
| **解决哪一段** | **预算授权 → 交付 → 验收 → 付款/退款/争议 → 声誉** |
| **信任模型** | 托管信任。Evaluator 必须是可信的（Client 自己 / 第三方），引入"人"的判断 |
| **适合** | 大额、需验收、交付周期长的任务（审计、开发、设计） |

### 对比总结

```
         x402                          ERC-8183
     ─────────────                  ─────────────────
     "一手交钱一手交货"              "先干活再验收再放款"
     
     支付层                           结算层
     HTTP 原生                        链上状态机
     无托管                           智能合约托管
     即时结算                         验收后结算
     适合：API / 微服务               适合：项目 / 任务制
```

### 它们如何组合

一个完整的 Agent 商业系统可以**同时使用两者**：

```
ERC-8183  → 锁定大额预算，管理任务全生命周期
    │
    ├── 执行阶段：Agent 可能调用数十个 API
    │      └── x402 ──→ 每次 API 调用按需付费
    │
    ├── 交付：内容哈希上链
    │
    └── 验收后：ERC-8183 Escrow 释放资金
```

## 六、与 ERC-8004 的关系

ERC-8004（Trustless Agents）提供**身份 + 声誉基础设施**：

- **Identity Registry**：Client 通过 ERC-8004 发现 Provider Agent，确认其身份和端点
- **Reputation Registry**：每次 ERC-8183 的 `complete`/`reject` 结果写入声誉 → 影响未来 Client 的选择
- **Validation Registry**：若有第三方验证 Agent 的能力（zkML / TEE），验证结果也写入 ERC-8004

> **三者关系**：ERC-8004 = 身份层（发现 & 信任），x402 = 支付层（小额即时），ERC-8183 = 结算层（大额托管验收）
