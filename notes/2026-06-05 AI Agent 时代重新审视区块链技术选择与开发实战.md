## 一、上半部分：重新审视区块链技术选择

### 核心论点：AI Agent 正在移动 Web3 选型的临界点

**过去的状态**：
- 只有强依赖去中心化的应用（如 DeFi）才愿意采用区块链
- 大量"中间地带"的应用因为成本过高而放弃

**临界点 = 成本 vs 收益的比较**：

### 📉 成本侧：正在被降低

1. **基础设施改善**
   - 性能：Layer2 方案持续提升吞吐量、降低交易成本
   - 案例：Conflux 主网升级后处理速度达 15,000 TPS，费用极低
   - 隐私：ZK 等密码学技术让隐私敏感场景也能上链

2. **AI Agent 降低用户侧成本**
   - Agent 可引导/教育人类用户理解区块链概念
   - Agent 作为自然语言→链上交互的接口
   - Agent 本身成为区块链"职业用户"（例：Yo 项目 — Agent 在 GitHub Actions 中运行，Sponsor 提供资金，Agent 完成需求"打工养活自己"）
   - 对 Agent 而言，链上交互和 API 调用没有本质区别

3. **AI Agent 降低开发者侧成本**
   - Rust 类比：AI 辅助编程降低 Rust 学习门槛 → 类似变化在区块链开发中发生
   - 开发者仍需理解区块链概念，但 AI 可大幅简化：合约雏形构建、ABI 解释、测试用例、部署脚本、失败交易排查、安全 review
   - 普通工程团队也能完成更多开发/调试/维护工作

### 📈 收益侧：更容易兑现

- Agent 时代出现更多**跨系统、跨服务、跨主体**的任务
- Agent ↔ Agent 交互天然需要中立协调层
- 区块链擅长：把状态/规则/资产权限放在多方可验证的环境中统一处理
- 各方拥有共同认可的信息源（链上状态），基于链上状态和规则协作

### 核心观点总结

> 过去问：**"你为什么要用区块链？"**
> 未来问：**"你的应用为什么不采用区块链？"**

## 二、下半部分：AI Agent 深度参与的区块链应用开发实战

### 关键概念：本质复杂性 vs 附属复杂性

引用 Brooks（《人月神话》作者），1987 年论文《No Silver Bullet》：

| 类型 | 定义 | 区块链开发例子 |
|------|------|---------------|
| **本质复杂性** | 来自于"要解决什么问题" | 投票方案选择（快照 vs 质押）、信任边界、链上/链下分工 |
| **附属复杂性** | 来自于"要怎么解决" | 前端实现、钱包交互、测试用例、部署脚本、调试 |

⚠️ 注意：两种复杂性的归属**随系统边界和目标变化**（如 DEMO 阶段前端是附属，产品化阶段就是本质）

### 五步开发演示（链上投票 Demo）

#### Step 1：确认需求（处理本质复杂性）
- 与 Agent 交互式澄清需求 → 发现不清晰的边界
- 控制 Agent"盘问"深度：核心决策自己定，细节可让 Agent 自行决策
- **产出物**：
  - PRD（产品需求文档）— 通过 `two-pard` skill 将决策转化为结构化 PRD
  - Issues Plan — 垂直切片，按用户故事拆分
  - Implementation Plan — 执行路径规划

#### Step 2：实现（委托附属复杂性）
- **Roughloop 模式**：每次给全新上下文的 Agent 分配一个子任务 → 任务完成 → 清上下文 → 新 Agent 接下一个任务
- 关键：
  - 每个任务明确验收目标和可验证对象
  - 整体交付前 Agent 自行与 PRD/设计决策比对
  - 推荐 `Implementation Notes`：记录 Agent 自行做出的设计决策（增强可观察性）
- 实测：33 分钟完成链上投票 Demo 全部实现

#### Step 3：调试
- 给 Agent 提供合适的工具（Harness）：
  - 链交互：compiled-dev skill
  - 前端调试：Computer Use（直接控制浏览器 + 钱包插件）
- Agent 可以自行闭环验证边界 case

#### Step 4：部署
- 附属复杂性高的"脏活"适合 Agent
- 只需告诉 Agent 目标网络 + 验证目标
- Agent 自行：写部署脚本 → 规划文件路径 → 配置网络 → 部署 → 验证

#### Step 5：合约升级
- 重复 Step 1~4 的流程
- 关键决策人工保留：测试网升级暂不由 Agent 执行（手动确认）
- 着重验证：升级是否破坏存储结构 / 引入不可逆安全问题
